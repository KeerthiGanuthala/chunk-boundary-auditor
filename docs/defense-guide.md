# Defense guide: chunk-boundary-auditor

How to talk about this repository in an interview. Every number here is checked against
`docs/metrics.json` by the same tool that checks the README, so what you say aloud matches what the
code produces.

## The 30 second version

"A chunker's output cannot show you which facts it split across a boundary, because the fact is in
the document and in no chunk. So I built a fixture where I plant every fact on purpose, with the
exact spans a reader needs, render it to real PDFs, and count the facts that no single chunk holds.
Two things came out that I would not have guessed: the extraction step loses more facts than any
chunker, and a small overlap can make the recursive splitter worse."

Then stop. The question that usually comes next is "worse how?", and the answer is in the second
claim below.

## The claims, each with how it is proved

**Claim 1: the usual extraction fix loses facts before any chunker runs.**
Command: `chunkaudit audit --mode sorted` (exits 1 with the reason printed).
Numbers: `sort=True` breaks 122 of the 396 planted facts, 30.8 percent of every fact in the
fixture, all on two-column pages. Block clustering breaks 0 of the same facts.
If pushed: "the fixture's two-column pages are generated by me, so I checked the mechanism, not
just the count: `chunkaudit extract D02 --mode sorted --page 1` shows the two columns interleaved
line by line, and `blocks` mode clusters text blocks by their left edge and reads each column top
to bottom. The loss is a property of position sorting on any two-column page, not of my PDFs."

**Claim 2: overlap is not free, and for one strategy it is not even positive at first.**
Command: `python experiments/exp02_overlap_sweep.py`.
Numbers: for fixed windows an overlap of 64 tokens recovers every orphan at 13 percent more chunks.
For the recursive splitter, 32 tokens of overlap loses 1 more fact than no overlap at all, and
64 tokens loses 4 more; it reaches zero at 256 tokens of overlap, with the index 61 percent larger.
If pushed: "the carried pieces are whole sentences or table lines; they take room at the head of
the next chunk, so a cross-paragraph pair that used to fit at the tail is pushed apart. It is the
same mechanism the framework splitter uses, which is why I reimplemented it rather than importing
it: I needed to see where each boundary fell."

**Claim 3: at the policy size the best strategy still loses facts, and the kind tells you why.**
Command: `chunkaudit audit`.
Numbers: sentence packing still orphans 5 facts at the policy size of 512 tokens. Fixed windows
lose 17 facts (4.3 percent of planted facts); the recursive splitter loses 20; page-aware windows
lose 51, including all 36 cross-page facts.
If pushed: "the recursive splitter and paragraph packing lose the same 20 facts at this size,
because at 512 tokens every paragraph fits and the separators below paragraph level never fire.
That is a property of the fixture's paragraph lengths, and I say so."

**Claim 4: every figure is machine-checked.**
Command: `make receipts`, then change any number in the README and run it again.
Numbers: 254 tests, 99 percent line coverage, 4 experiments, 5 decision records.
If pushed: "the checker matches anchor phrases, not digits, because a digit that happens to
appear elsewhere would pass a stale sentence. The README tables and the banner are generated from
the experiment JSON, and CI fails if they drift."

## Questions that are meant to be hard

**Isn't this just a wrapper around PyMuPDF and a few string splits?**
The splits are the smallest part. The work is the fixture design (facts with recorded spans in
layouts that break extraction), the containment metric with its three outcomes, and the receipts
that keep the prose honest. PyMuPDF renders and reads; everything that decides what a loss is and
attributes it is in this repository.

**The corpus is synthetic. Does any of this transfer?**
The direction transfers; the rates do not, and the README says so in its own section. Position
sorting interleaves two-column pages on any PDF. A token window cuts inside sentences on any text.
What does not transfer is "a strategy losing 1.3 percent of the planted facts here loses about that
much in production", and that claim is not made. The first item of future work is planting facts in
real documents, and the corpus module records spans per fact so that is an annotation format, not a
rewrite.

**Why containment and not retrieval quality?**
Because retrieval quality blames the whole pipeline at once. Containment is the one condition the
chunker alone controls, and it is necessary: a fact in no chunk cannot be retrieved by any model.
Measuring it first means the embedding model only gets blamed for what is left.

**What is the weakest part?**
The tokenizer. Sizes are in the repository's own tokens, so 512 here is not 512 BPE tokens, and I
cannot say where a production size falls on the sweep. I chose that over a tokenizer that downloads
on first use because reproducibility from a clean clone mattered more for this repository than
comparability with a specific model. A BPE tokenizer behind an optional extra is on the future
work list, with the sweep re-run under both.

**Why did you reimplement the splitters instead of using the framework ones?**
Two reasons. The audit has to say where a boundary fell and why, and a framework splitter changes
its boundary rules between versions. And the recursive overlap result would have been impossible
to explain without reading the carry logic. The shapes are faithful; ADR-002 says they are faithful
to the shape, not to any version's code.

**What would you do differently with more time?**
Hyphenation and scanned pages in the fixture, because they are the two extraction losses this
fixture cannot see, and I know that is where real ingestion pipelines lose the most.

**Did the measurement find anything you did not expect?**
Four bugs in my own code, each with a commit and a test. The one I would tell first: sentence
packing orphaned a one-sentence fact, which should be impossible, because extracted PDF text has a
newline at every line wrap and my splitter treated each newline as a sentence end.

## Things to say and things not to say

Say:
- "contained, orphaned or broken, and broken means extraction lost it before any chunker ran"
- "zero over 396 facts, so a resolution floor of one in 396"
- "comparable with each other and with nothing outside the fixture"
- "cost against benefit: 13 percent more chunks for every orphan recovered, for fixed windows"

Do not say:
- "block clustering never loses a fact" (say: broke 0 facts on this fixture, below one in 396)
- "sentence packing is the best strategy" (say: lost the fewest facts on this fixture at this size)
- "512 tokens" without "in the repository's own tokenizer" the first time
- "the recursive splitter is bad" (say: its overlap carry moves boundaries without protecting them
  until the overlap is as large as the unit it carries)

## The live demo script

```bash
chunkaudit audit                                        # the headline table, exit 0
chunkaudit audit --mode sorted                          # 122 broken, exit 1 with the reason
chunkaudit explain D06-single-1 --strategy sentence_window   # the war story, span by span
python experiments/exp02_overlap_sweep.py               # overlap priced: recovered against growth
make receipts                                           # every number re-measured and checked
```
